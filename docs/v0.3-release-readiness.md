# v0.3 Release Readiness Report

Consolidated record for the `v0.3-production-ready` branch, covering everything
between v0.2.0 (`29e44df`, "Release v0.2.0") and HEAD (`3c3a57b`,
"docs: align APIs and fix examples").

- Scope: 29 commits (`git rev-list --count 29e44df..HEAD` = 29; by prefix:
  20 `fix`, 4 `test`, 2 `docs`, 1 `ci`, 1 `chore`, 1 `perf`). Note: earlier
  round notes said "27"; the actual count at HEAD is 29.
- Evidence: `target/*.log` (169 overnight logs + 4 r6 spot-check logs),
  `target/bench-results.md`,
  `target/overnight-plan.md`, `CHANGELOG.md`, plus two fresh spot-checks run for

## 1. Executive summary

Between v0.2.0 and HEAD the library gained: hard bounds on every
server-controlled allocation dimension in both engines (framing, item counts,
column bytes, response totals, exception-chain depth), real connect/setup
timeouts in both engines, cancellation that actually stops server-side queries
(async mark-and-discard, Python borrow-free `discard()`), a correct Python
connection pool (lending state machine + dedicated acquire executor), a fix for
the multi-frame compressed-response P0 that had made *any* compressed SELECT
fail on the sync path and >= ~1 MiB blocks fail on the async path, pyo3
0.29.2 (closing two RUSTSEC advisories) with free-threaded 3.14t wheels, CI
repairs (nextest profile flag, true MSRV 1.89 enforcement, version gates), and
a P1 performance pass (bulk offset reads, merged String body reads, large-read
bypass, pool try-lock sweep). Validation breadth: full workspace suite x3 at
637/637 plus a fresh 673/673 at HEAD with creds, Python 3.12/3.13/3.14t
full suites (160/160 at HEAD on 3.14t), live TLS/SSH containers, a
29-case compression matrix under forced LZ4 and Zstd, multi-GB memory-stability
and pool-churn runs, 8-target libFuzzer campaign (5 targets' 600 s logs
preserved on disk, 3 clobbered by a failed re-launcher — no crash artifacts
anywhere), cargo audit/deny clean.

**Verdict: production-ready for the 0.3 tag.** Every P0 found overnight was
root-caused, fixed, regression-tested, and re-validated live. Caveats, none of
which block the tag:

1. README INSERT/ALTER benchmarks are stale on ClickHouse 26.7+ (server-side
   ~60 ms per mutation; client adds ~0.3 ms) — annotated in README, numbers not
   re-baselined.
2. LowCardinality key-serialization version 2 (server-side nested format) is
   rejected by the readers; only version 1 is parsed (`src/connection/io.rs`).
3. `--no-default-features` (no-tokio) rustdoc build still has 2 warnings
   (`src/builder.rs:17`, `src/error.rs:35`).
4. Two warning-severity, unpatched-upstream advisories remain (paste
   unmaintained; event-listener `!Send` StackSlot) — indirect/dev-side only.
5. Fuzz ASAN legs were not run (need a nightly toolchain); 3 of 8 fuzz legs
   lack preserved 600 s logs on disk (plan records them clean; artifacts dirs
   are empty).
6. GitHub Actions could not be exercised live (org-level `startup_failure`,
   external); ci.yml verified with actionlint 1.7.12 only.
7. Python 3.15 is untested in CI (abi3 wheel is forward-compatible by design).
8. Minor known gaps carried to 0.4 (§6): schema-cache clone-per-hit and
   whole-cache DDL clear, per-row String loop in the async raw reader, idle-ping
   stray-Pong drop window, `python_bench.py` hardcoded credentials.

## 3. Audit streams and overnight rounds

### A. Correctness / soundness — decoding, framing, wire fidelity, compression

- **Decoding hardening** (`5b56206`): varints outside `u64` rejected instead of
  panicking or truncating; malformed LC dictionaries/indexes return protocol
  errors instead of panicking or zero-filling; Date32 uses its signed 4-byte
  wire representation everywhere (compressed blocks, dynamic decode, LC
  dictionaries).
- **Wire fidelity** (`be60a09`, `3ec9f8d`): the buffered (decompressed-buffer
  and sync-buffer) parsers now share `shared/skip_column.rs`, framing nested
  columns identically to the raw stream readers. Previously Array/Map offsets
  were parsed as varints (async) or skipped (sync), JSON serialization-version
  bytes leaked into data, LC columns desynced whole blocks, and the sync parser
  hung on the zero-row LC header block of every SELECT containing an LC column.
  `tests/native_wire_fidelity_test.rs` (351 lines) pins the layouts.
  `3ec9f8d` adds `#[repr(transparent)]` to the Decimal newtypes (layout
  guarantee relied on by slice views).
- **Query-ID interop** (`5912c8a`, `932e3f4`): sync and async builders now draw
  from one process-wide `st-ch-` generator; mixed workloads no longer collide
  with `QUERY_WITH_SAME_ID_IS_ALREADY_RUNNING` (error 216).
- **Compression P0** (`ecd320a`), three root causes, all fixed:
  1. *Async multi-frame*: ClickHouse flushes its ~1 MiB
     `CompressedWriteBuffer` mid-packet, so a Data packet body larger than
     ~1 MiB arrives as >= 2 compression frames; the async reader consumed
     exactly one frame per packet, leaving frame remnants in the stream
     (`protocol error: unexpected end of buffer skipping column data`).
     Deterministic at >= 15,000 rows x ~73 B; the failing frame decompresses to
     exactly 1,048,576 bytes; `max_block_size=8000` masked it, `=20000` forced
     it; reproduced on CH 24.8 and 26.7, LZ4 and Zstd.
  2. *Sync never decompressed*: the sync query packet has always set the
     compression flag, but the response read path never decompressed — ANY
     compressed SELECT failed; a 20,000-row query wedged until the server's
     300 s read timeout because the client also sent its trailing empty Data
     block uncompressed, which the server tried to parse as a compression frame.
  3. *Trailing-block asymmetry*: fixed together with (2) — the client's
     trailing empty Data block is now compressed whenever the query packet's
     compression flag is set, on every path that sends one (plain and
     parameterized queries, block INSERT, execute-style statements).
  Fix model: a continuous decompressing stream per packet body (the
  clickhouse-cpp `CompressedReadBuffer` model) pulls the next frame only when
  the current one is drained; cumulative decompressed size bounded by
  `MAX_BLOCK_BYTES` (1 GiB) on top of the per-frame cap. The Python wheel
  inherits both fixes.
- **Streamed-block semantics** (`db0ecb2`, `d1301a7`): `.block()`/`fetch::<Block>()`
  now error on multi-block results instead of silently dropping rows; async
  `execute()`/`end()` and sync `drain_response()` surface server exceptions.

### B. Pooling

- **Python exclusivity** (`441cca9`): the lending state machine eliminates
  double-lending of freshly grown connections, duplicate deque entries, slot
  resurrection after `close()`, and zombie slots; factory/ping run outside the
  condition lock; growth can never exceed `max_size`; `release()` idempotent;
  truthful `in_use` + `creating` metrics.
- **Acquire starvation** (`6244d23`): found by the benchmark pass (§4) — 32
  concurrent SELECT 1 on the default pool(4) deadlocked into the 30 s
  `pool_acquire_timeout` because acquire waiters and slot-freeing query work
  shared one bounded executor. Dedicated acquire executor + single-point
  release; 32/64-concurrency bursts now complete in milliseconds; regression
  tests in `test_pool_concurrency.py`.
- **Try-lock sweep** (`596e314`): `SimplePool::get` sweeps `try_lock` from the
  assigned index before blocking, removing head-of-line blocking (measured
  ~1,400x on the contended 2-slot scenario; see §4).
- **Churn validation** (R3, `r3-pool.log`): Rust 10k sequential + 3x500
  concurrent at pool sizes 1/4/8 — zero errors, concurrent throughput 2,811 /
  8,172 / 12,426 q/s (verdict-line figures 2,561/8,089/12,318); Python same
  churn 2,138/5,244/6,707 q/s concurrent, pool grows exactly to `max_size`,
  metrics settle `in_use=0, creating=0`.

### C. Timeouts / cancellation

- **Connect watchdogs** (`4a71150`): sync — every resolved address tried, per
  attempt `connect_timeout`, whole setup (TLS + handshake + addendum) under one
  absolute deadline enforced by a socket-shutdown watchdog with temporary I/O
  timeouts as fallback; setup expiry is `sync::Error::Timeout`.
  Async — `connect_timeout` bounds the whole `connect_raw` future (TCP + TLS +
  handshake + addendum + Ping); `Duration::ZERO` rejected as `Error::Config`.
- **Async cancellation safety** (`aebe934`): in-flight response mark owned by
  the task holding the guard; a future dropped mid-response discards the socket
  (exactly one clean reconnect) instead of returning a mid-response socket to
  the pool. `SimplePool::drop` no longer writes an unframed Cancel byte through
  chunked/TLS transports. Chunked-receive reentrancy fixed (a `Pending` between
  chunk length and payload no longer serves zero-fill bytes).
- **Python kill-on-cancel** (`8ef632b`): `CancelledError` handlers now call
  borrow-free `_Client.discard()` instead of the dead `await cancel()` —
  `SELECT sleep(3)` no longer runs to completion as a zombie; pool slot is
  destroyed and transparently replaced; abandoned streams kill rather than
  recycle (`_QueryStream.eos`).
- **Fail-closed cancels** (`3c3a57b`, and the Rust core earlier): async
  `Client::cancel`, sync `SyncClient::cancel`, and Python `cancel()` all return
  guidance errors instead of sending stray Cancel packets; documented
  alternatives: query deadlines, drain-to-EndOfStream, shutdown handles,
  Python `discard()`.

### D. Resource security

- **Framing caps** (`112332f`): 64 MiB on chunk lengths and compression-frame
  sizes before any allocation (previously a 4-byte header could drive a 4 GiB
  sync / 1 GiB async allocation); checksum computed in place; zstd output
  bounded during decompression; encode paths use checked `u32` conversions.
- **Count caps** (`8a5ac37`): password rules, ignored PartUUIDs, JSON paths,
  Dynamic subcolumn names, LC dictionary keys, block columns/rows — all capped
  before sizing any allocation or read loop, in both engines (previously
  `u64::MAX` counts could capacity-overflow panic the client).
- **Byte caps** (`1c12904`): `MAX_STRING_BYTES` (16 MiB-1) per String/JSON
  value, `MAX_COLUMN_BYTES` (64 MiB) per column across raw/materialized/discard
  readers, monotonic Array/Map offsets with a 10M inner-row cap, LC index-count
  equality, Variant compact-granule bound (previously multi-TiB eager
  allocations from a few wire bytes).
- **Response budgets** (`a9d2939`): cumulative `max_response_size` (256 MiB
  default) on all retaining query APIs, both engines, with deterministic
  connection recovery; streaming APIs intentionally unbudgeted (per-block
  bounds).
- **Exception-chain cap** (`650b065`): `MAX_EXCEPTION_CHAIN_DEPTH=1000` at all
  four parse sites; 16 new tests; seeded fuzz corpus at the exact boundary.
- **pyo3 advisories** (`2e58fb6`): 0.28.3 -> 0.29.2 closes
  RUSTSEC-2026-0176 (OOB read in `BoundListIterator`/`BoundTupleIterator`
  `nth`/`nth_back`) and RUSTSEC-2026-0177 (missing `Sync` bound in
  `PyCFunction::new_closure`). Neither path is exercised by our bindings, but
  the affected code shipped in every old wheel.
- **Fuzz results** (R4, pristine `ecd320a` worktree, `-s none`, 600 s/target):
  on-disk logs substantiate block 1,569,304,729 units, chunked 179,345,459 +
  181,955,797 units (two runs), coordinator 295,212,362, varint 264,379,435;
  exception re-run post-cap-fix 68,179,007 units in 121 s with the seeded
  cap-boundary corpus. The `column_bytes`, `lc_variant`, and `ssh` logs were
  clobbered by a later failed launcher (`EXIT:127`, binary missing at that
  moment); the overnight plan records all 8 targets clean at 600 s each. All
  artifact directories are empty — no crash artifacts for any target. ASAN
  legs skipped: `-Zsanitizer` needs nightly, only stable 1.95 installed
  (`r4-fuzz-driver`).
- **Audit/deny** (R4): `cargo audit` exit 0, 0 vulnerabilities, 2 warnings
  (paste 1.0.15 unmaintained RUSTSEC-2024-0436; event-listener 5.4.1
  RUSTSEC-2026-0221) — both indirect/dev-side, no patched release upstream
  (`r4-audit`). `cargo deny advisories sources licenses` all ok after adding
  "Apache-2.0 WITH LLVM-exception" to the allow list (`r4-deny`, committed in
  `650b065`).

## 6. Known limitations and 0.4 follow-ups

1. Org-level GitHub Actions `startup_failure` (external): CI never ran live
   overnight; ci.yml is file-verified via actionlint only.
2. README INSERT/ALTER timing drift on CH 26.7+ (~60 ms server-side per
   mutation): annotated with a dagger, numbers not re-baselined.
3. LowCardinality nested key-serialization v2 server format unsupported
   (readers accept version 1 only; v2 is rejected with a protocol error).
4. ASAN fuzz legs need a nightly toolchain in CI (stable-only tonight; `-Zsanitizer`).
5. No-tokio rustdoc build has 2 warnings (`src/builder.rs:17`,
   `src/error.rs:35` — `crate::Client` does not exist without tokio).
6. Schema-cache P2: `schema_for_table` clones the `TableSchema` on every hit,
   and DDL that may change schema clears the whole cache, not one table.
7. Async raw-capture String loop is still per-row (documented in-code); fully
   buffered parsing needs a stream-pushback design.
8. Async idle-ping stray-Pong drop window: `is_connection_alive` reads one
   byte expecting Pong within 1 s; a delayed/stray reply can drop a live
   connection (bounded cost: one reconnect).
9. `python_bench.py` (and 4 Rust bench bins) hardcode `default`/`test`
   credentials — need env-override support before they run against the honne
   server without a driver shim.
10. Python 3.15 untested in CI; the abi3-py312 wheel is forward-compatible by
    design and 3.15 is deliberately not claimed in classifiers.
11. Fuzz-log preservation: 3 of 8 legs' 600 s logs were overwritten by a failed
    re-launcher; keep per-target immutable log paths next campaign.
